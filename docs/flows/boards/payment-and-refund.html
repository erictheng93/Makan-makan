收款、退款與班次

碰錢的每一個寫入路徑，至少有冪等鍵、金額上限、狀態守衛其中一項。這張圖把它們攤開。

全景板：master user flow
流程文件：11-floor-cashier.md
對照原始碼：2026-08-21

開班 → 收款 → 結班

1

啟用收銀機、開班

一台收銀機同時只能有一個 active 班次。開班現金會寫成一筆 opening 現金流動。

POST /pos/registers/:id/activatePOST /pos/shifts/start此收銀機已有活躍班次
2

帶出訂單

UUID、order_number、client_mutation_id 三種識別碼都收，由 resolveOrderIdentity 收斂。

GET /api/v1/orders/:id
3

送出收款

強制要求 Idempotency-Key：重送同一把鍵會回傳第一次的結果，不會重複扣款。

POST /api/v1/paymentsidempotencyMiddleware requireKey
4

可付款狀態檢查

isAlreadyFinalized 同時看 status 與 payment_status。

409 ORDER_NOT_PAYABLE
5

金額核對

以 orders.total_amount_cents 為準。全額、部分付款總和、expectedTotal 三者各有錯誤碼。金額不得超過兩位小數。

PAYMENT_TOTAL_MISMATCHPAYMENT_AMOUNT_MISMATCHPARTIAL_PAYMENT_TOTAL_MISMATCH
6

結清訂單

條件式 UPDATE：payment_status NOT IN ('paid','completed','refunded','partial_refunded')，所以兩台收銀台同時結清只有一台生效。

payment_status = paidorders.status → paid
7

寫交易與稽核

payment_transactions 與 payment audit 於同一批次寫入。

PAYMENT_AUDIT ATTEMPT
8

結班

預期＝開班現金＋期間銷售−期間退款；差額＝實際清點−預期。差額不會擋住結班，只被記錄。

POST /pos/shifts/:id/enddifference_amount_cents寫入 closing 現金流動、清空 currentShiftId

退款的三條路

路徑端點角色關鍵守衛
POS 退款 POST /pos/refunds/create 0 / 1 / 4 已 completed ＋ processing 的退款都算進已退金額，超過訂單金額即拒絕
金流交易退款 POST /payments/refund 0 / 1 / 4 累計退款不得超過原交易金額；全額退則 refunded，否則 partial_refunded
市集整筆退款 POST /market-checkouts/:id/refund 僅 0 須有付款紀錄；provider split 另需 providerTransactionId，且狀態須為 paid／partial_paid

結班後的退款走另一條路

  • 退款若指向已結班的班次，仍可建立，但不寫現金流動——已結的帳不能再被動。
  • 改在退款列的 metadata 標記 postCloseAdjustment: true，退款列本身就是調整紀錄。
  • 只有明確 closed 的班次觸發這條路；active／suspended／查不到都走正常流程。

退款完成必須是同步的

  • 舊版用 setTimeout 模擬 PSP 回調，但 Workers 不保證回應送出後的計時器會執行。
  • 結果是退款永遠卡在 processing。
  • 現在在回傳前就把終態寫完。不要改回非同步。
