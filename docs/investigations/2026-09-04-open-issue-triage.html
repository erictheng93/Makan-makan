它們看起來是四個獨立的 bug，實際上是同一條付款資料流上的四個斷點。照編號或照難易度修，會在錯的基礎上調數字。

為什麼是這個順序

  1. #311 必須最先。它決定 payment_status 的正規值。#310 要實作 updatePaymentStatus，在詞彙定調前寫，就是再多一個要改的寫入點。
  2. #310 在 #312 之前。#312 的營收目前以 orders.status IN (paid, delivered, served) 為準，而 #310 證明店主按「更新」就能把狀態推到 paid 卻沒有收到錢。先修 #312 的 status 過濾，數字仍然含這種「按出來的」訂單。
  3. #326 可以並行。它在下單路徑上，與付款狀態無關，唯一的相依是不要和 #310 同時改 orders 的寫入而互相衝突。

#311 · 付款狀態詞彙分裂

issue 的修法方向正確，但範圍要擴大兩處，同時有一個好消息。

現況是三套詞彙在打架

層詞彙
正規型別 ORDER_PAYMENT_STATUSESpending · completed · failed · refunded
實際寫入（3 個服務）pending（預設） · paid · refunded · partial_refunded
守衛（防重複付款／退款）paid · completed · refunded · partial_refunded

completed 與 failed 在全 repo 都沒有任何寫入點。宣告的四個值裡有兩個是空的，而真正會寫的兩個不在集合裡。

issue 漏掉的兩處

  • 第三個寫入點。pos/services/MarketCheckoutPOSPaymentService.ts:339 也把 "paid" 寫進 orders 表。issue 只點名了 PaymentService 的兩處。
  • partial_refunded 同樣不在正規集合。refundPayment.ts:102 部分退款時寫這個值，讀回來一樣變成 pending——與 paid 完全相同的故障，只是走另一條路。
好消息：不需要動任何守衛。三個守衛都已經同時接受 paid 與 completed—— payableGuard 的 NOT IN ('paid','completed','refunded','partial_refunded')、 isAlreadyFinalized 的同名清單、refundPayment 的負向清單 NOT IN ('pending','failed','cancelled','refunded')。 收斂到 completed 是三個字面值 + 一個型別的改動，不碰控制流。
時間成本只會上升。production 目前七筆訂單全是 pending，零筆需要遷移。 一旦有第一筆真實付款進來，就要多寫一支 backfill。

不要一起改的

GroupOrdersService:2512 寫的是 splitBills 表、MarketCheckoutPaymentProvider 寫的是 market checkout 自己的表。那些網域的 paid 是合法詞彙。掃描要用「打在 orders 表上」而不是「字面值是 paid」為準：

pat = re.compile(r"\.update\(\s*orders\s*\)(.{0,700}?)\.where", re.S)

#310 · 付款狀態在後台無路可寫

三項主張全部複驗成立，另外找到一個讓它「看起來有覆蓋」的假象。

updatePaymentStatusSchema 其實已經寫好了（validation.ts:184），只是沒有任何路由掛它。所以連請求驗證都備好了，差的只有端點與實作。

它的測試鎖住了空殼。OrdersService.test.ts:898-902 斷言的是 「回傳的 order id 是 42」與「快取被清掉」，完全沒有斷言付款狀態有被寫入任何地方。 所以這兩個測試在一個什麼都不做的空殼上是綠的，方法看起來有覆蓋。

可以先切出來的一項

前端 canCancel 只允許 pending/confirmed，但伺服器的 ORDER_STATUS_TRANSITIONS 允許 preparing → cancelled 與 ready → cancelled——前端比後端更嚴。這一項不依賴 #311，是純前端判斷式放寬，可獨立成一個 commit，而且是三項裡最直接影響店主日常的：客人中途走人時，目前只能把單一路推到 paid，那正是「進死路」的入口。

#312 · 數據分析

實際是三個缺陷，不是兩個。而且修法有一個很容易做錯的細節。

totalOrders 絕對不能一起加過濾。它是轉換率的分母 （completedOrders / totalOrders）。順手一起過濾，分子分母變同一個集合， 轉換率永遠是 100%。正確做法是把一個查詢拆成兩個： A 不過濾出 totalOrders，B 過濾出 totalRevenue + averageOrderValue。 AOV 必須與營收同一個查詢，否則會算成 570/7 而不是 570/4。

缺陷二：不只「本月」，每一個期間都是滾動視窗

選項實際
今日✅ 真的是日曆邊界
本週 / 本月 / 本季 / 本年❌ 最近 7 / 30 / 90 / 365 天

缺陷三（issue 未提）：同一畫面兩個端點拿到不同區間

const map = { today:"today", week:"week", month:"month",
              quarter:"month",   // ← 本季被映射成 month
              year:"year" };

選「本季」時，/analytics/performance 收到 90 天的日期範圍，而 /analytics/dashboard 收到 period=month。這是與 status 過濾獨立的第二個成因——修好過濾後，選本季時兩半仍然對不起來。

#309 · 系統設定靜默丟棄

後端完全有能力接收。這是純前端修正，範圍縮小到一支檔案。

  • restaurantSettingsSchema 明確宣告了 minOrderAmount、autoAcceptOrders、timezone、maxOrdersPerHour，其餘靠 .loose() 放行。
  • 餐廳名稱／電話／地址是頂層欄位，updateRestaurantSchema 由 .partial() 產生，全部可選、全部收。
  • 寫入是合併不是覆蓋（{...existingSettings, ...incomingSettings}），所以分批送出不會互相洗掉——這原本是最大的風險，實際上不存在。

不需要動 API、不需要 migration、不需要部署 Worker，只要 Pages。

驗收不能看 UI 訊息。這張的本質就是「UI 報成功但值沒離開瀏覽器」， 任何以 UI 訊息為準的驗收都會重現同一個假象。條件是：改值 → 儲存 → 重整 → 值還在。
