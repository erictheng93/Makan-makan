備註

六個容易誤解的地方

控制平面是分開的

  • 租戶、授權、部署、入駐走 management-api，與各店營運的主 API 分開部署、分開網域。
  • management-api 同時綁 MANAGEMENT_DB 與 PLATFORM_DB——核准入駐時一次寫兩個資料庫，靠補償而非交易維持一致。
  • 主 API 反向透過 service binding MANAGEMENT_API 呼叫它，不走公開網路。
  • 兩邊的權杖不通用：staff JWT 打不進管理 API。

Durable Object 的本體在 realtime

  • RealtimeSession 的 class 定義與 migration 都在 realtime Worker。
  • 主 API 是跨 script 綁定（script_name = "makanmasak-realtime-prod"），所以兩者的部署有順序關係——realtime 先上。
  • REALTIME_SESSION 沒綁定時廣播會靜默跳過並回報成功，訂單狀態照樣寫入 DB。

菜單圖片不經主 API

  • 後台直接打 image-processor（VITE_IMAGE_API_URL），由它寫進 R2 IMAGES_BUCKET。
  • 主 API 的 Env 型別雖然宣告了 IMAGES_BUCKET，它的 wrangler.toml 沒有這個 binding——那是殘留宣告，不要照著用。
  • 主 API 的 R2 只有 BACKUP_STORAGE。

排程幾乎都在主 API

  • 主 API 掛 8 條 cron：token 清理、用量彙總、市集對帳、揪團過期、帳務週期、試用回收、代幣到期等。
  • image-processor 有 1 條（每日 01:00）。
  • backup-scheduler 的 crons 是刻意留空的。災難復原靠的是 makanmasak-prod 上的 D1 Time Travel，與那個 Worker 無關。空陣列才會在部署時清掉既有排程，刪掉整個區塊反而會讓舊排程繼續跑。

限流是分層的，不要合併

  • 最底層是 GLOBAL_RATE_LIMITER（每 IP 每 60 秒 100 次）。
  • 訪客下單另外疊一層每（餐廳, IP）的節流。
  • 把全域限流器改成以餐廳為 key，會讓攻擊者的額度乘上餐廳數量——反而更便宜。

wrangler 設定的兩個地雷

  • 不要重新加回 inspector_port。4 個 Worker 的 wrangler.toml 都刻意註解掉——任何值都會讓 Windows 上的 pnpm dev 直接 std::terminate。需要固定 DevTools 埠請用 CLI 旗標。
  • 新資料表一律建成 STRICT，否則 SQLite 會靜默把 TEXT 塞進 INTEGER NOT NULL 欄位；drizzle-kit 不會產生這個關鍵字，要手動補。
