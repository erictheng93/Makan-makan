# 店主總覽 (Owner Overview) E2E 使用流程草案

前提：使用者以店主身份登入 (`role=1`)，且能訪問 `http://localhost:3001/dashboard/owner-overview`。

以下流程可作為上線前最終測試的人工或自動測試指引。每一條都可拆成一個獨立測試案例（至少 15 條）。

## 1) 登入後進入店主總覽

- 目標：確認導覽與權限正確。
- 步驟：
  - 直接以店主帳號登入後導向 `/dashboard/owner-overview`。
  - 觀察頁面主標題與左側導覽是否在「owner-overview」高亮。
- 預期：
  - URL 為 `/dashboard/owner-overview`。
  - 頁面不應呈現未授權頁面。
  - 能看到「店主總覽」字樣（或對應 i18n 內容）以及 KPI/卡片區塊。

## 2) 初次載入資料成功

- 目標：驗證主要資料視覺化元件都可渲染。
- 步驟：
  - 重新整理頁面並等待請求完成。
- 預期：
  - KPI 卡片 4 張都顯示數值（不是 `--`）。
  - 即時訂單、員工活動、熱門商品、今日財務皆有對應區塊渲染。
  - 無全域錯誤提示（除非刻意模擬失敗）。

## 3) KPI 變化方向與文案一致性

- 目標：驗證今日營收/訂單成長趨勢的視覺邏輯。
- 步驟：
  - 觀察四張 KPI 卡片中的變化文案與圖示顏色。
- 預期：
  - 成長 >0 顯示上升、<0 顯示下降、=0 顯示穩定（可藉 icon/文字顏色判斷）。
  - 營收/訂單值單位與格式合理（營收使用幣值格式）。

## 4) 快速操作：新增員工

- 目標：確認 quick action 導向正確。
- 步驟：
  - 點擊「新增員工」按鈕。
- 預期：
  - 頁面導向 `/dashboard/employees`。
  - 新頁面可正常操作（例如可看到員工管理清單）。

## 5) 快速操作：更新菜單

- 目標：確認菜單維運入口可達。
- 步驟：
  - 點擊「更新菜單」按鈕。
- 預期：
  - 頁面導向 `/dashboard/menu`。
  - 可開啟菜單/品項管理介面。

## 6) 快速操作：查看報表

- 目標：確認分析入口可用。
- 步驟：
  - 點擊「查看報表」按鈕。
- 預期：
  - 導向 `/dashboard/analytics`。
  - 看到報表頁至少有可視化/資料框架可展示。

## 7) 快速操作：系統設定

- 目標：確認店主可進入系統設定。
- 步驟：
  - 點擊「系統設定」按鈕。
- 預期：
  - 導向 `/dashboard/settings`。
  - 仍保留店主權限可見內容（未被導向無權限頁）。

## 8) 即時訂單有資料時的顯示

- 目標：確認「即時訂單」欄位資料轉換正確。
- 步驟：
  - 模擬有進行中訂單（含 `tableId` 或 `orderNumber` 與 item 數量）。
  - 觀察列表前 5 筆。
- 預期：
  - 每筆包含桌號/項目數與狀態與時間文字。
  - 狀態標籤對應 `new/confirmed/preparing/ready/delivered` 轉譯合理。

## 9) 即時訂單空狀態

- 目標：驗證空資料 fallback。
- 步驟：
  - 模擬 active orders API 回傳空陣列（或清空場景）。
- 預期：
  - 顯示「目前無資料」（i18n 對應文字）。
  - 版面不崩壞，仍可操作其他區塊。

## 10) 員工活動顯示與狀態映射

- 目標：驗證前 6 名員工活動列表。
- 步驟：
  - 提供混合角色與 `status`（active / inactive）。
- 預期：
  - 名稱/角色欄位可讀。
  - 在線/忙碌/離線徽章顏色與文案一致（online/busy/offline）。
  - 人數少於 6 也不會崩潰。

## 11) 今日財務區塊精度

- 目標：確認「今日營收」「訂單數」「客單價」「預估月營收」邏輯。
- 步驟：
  - 在有資料狀態下觀察三大 KPI 與月估值。
- 預期：
  - 客單價 = 今日營收 / 今日訂單（整數或四捨五入規則一致）。
  - 月估值為 30 天乘上今日營收。
  - 無資料時呈現 0 或合理預設值，不拋錯誤。

## 12) 營收趨勢時間範圍切換

- 目標：驗證「7d / 30d / 3m」切換行為。
- 步驟：
  - 在下拉選單逐一切換三個選項。
- 預期：
  - 選項值更新，圖表區仍維持可見且不報錯。
  - 若有 API 依時間範圍變動，區塊內容應隨之更新。

## 13) 熱門商品列表排序與欄位

- 目標：確認前 5 熱門商品資訊完整。
- 步驟：
  - 在回傳資料時觀察排行榜排序。
- 預期：
  - 以返回順序顯示 Rank，從 1 開始遞增。
  - 每項顯示品名、銷售筆數、營收。
  - 無資料時顯示空狀態文案。

## 14) 系統健康狀態燈號

- 目標：驗證 API/DB/realtime 健康卡片與狀態文案。
- 步驟：
  - 在不同系統健康回應（healthy/warning/error）下觀察。
- 預期：
  - 狀態點與標籤對應一致（綠/黃/紅）。
  - 描述欄位有意義，且卡片不會因個別健康資料異常而整體消失。

## 15) 錯誤回復與定時更新行為

- 目標：覆蓋「讀取失敗」與「定期刷新」。
- 步驟：
  - 情境 A：模擬全部 API 失敗，驗證錯誤列是否出現與「重試」有效。
  - 情境 B：網路恢復後點「重試」，確認可重載。
  - 情境 C：維持登入狀態超過 35 秒，觀察是否有 30 秒輪詢刷新。
- 預期：
  - 錯誤列顯示且點擊重試會再次發送請求。
  - 資料成功回補後，錯誤列消失。
  - 輪詢觸發後即時訂單/員工/財務區塊可更新。
